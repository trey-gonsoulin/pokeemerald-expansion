# Overworld debug menu

The fork's debug menu improvements. The everyday gotchas for `src/debug.c` are in `CLAUDE.md`.

- Overworld debug menu improvements. The engine is fork-owned, in `src/debug_menu_ui.c` (API in `include/debug_menu_ui.h`): odometer numeric input and its digit highlight, list paging, scroll arrows, the submenu path window and the menu-position restore. `src/debug.c` keeps the menus, their state (`sDebugMenuListData`) and the hooks that call the engine.
  - Submenu labels (#88): the list drops an over-wide label to a narrower font by its whole width, which for a submenu is the arrow's x (110) plus the arrow, so `Debug_CopySubMenuLabel` fits the text alone to end by that x (its own font codes, the arrow kept in the menu font). No current label needs it. Covered by "Submenu label:" in `test/debug_menu_ui.c`.
  - Bounded labels (#280): the labels of the basic, Trainers, Mass Outbreak and Flags lists, and a submenu label's text, go into their 32-byte `itemNames` rows through `Debug_CopyLabel` (`src/debug_menu_ui.c`; `Debug_SetItemName` in `src/debug.c`), which cuts an over-long label off before any control code or two-byte character that wouldn't fit whole. No current label is cut. Covered by "Bounded label:" in `test/debug_menu_ui.c`.
    - The Recent warps rows, "Back to <map>" included, and Set Flag's and Set Var's name line (`Debug_CopyStringEndToFit`, a leading ellipsis and the end of a name too long or too wide) cut by bytes and could start inside a control code or a two-byte character: the skip now steps over whole characters and codes (`SkipLabelBytes`, through `GetLabelCharSize`), and the copies go through `Debug_CopyLabel`, so a code's 0xFF argument isn't read as the end (#283). Today's map, flag and var names are plain text, so nothing changed in game. A code whose arguments the EOS cuts short is still read past the EOS, as by `Debug_CopyLabel`. Covered by "Recent warp row:" in `test/debug_menu_ui.c`.
  - Name order (#12): on the species, item and move steps (`.names` on the `DebugSelectionStep`), Start jumps to the first name with the next initial letter, and Up/Down then step A-Z until another key turns it off. The first Start on each kind of step in a menu session sorts its range into `sDebugMenuListData->sortedNames[]` (`Debug_BuildNameOrder`, a multikey quicksort since #137: about 8 frames for the ~1,570 species, 4 for items or moves, where #12's merge sort took 18 and 9; scanning on every press took 4 frames per step), which `Debug_DestroyMenu_Leave` frees. Disabled species and unnamed items are left out. Covered by `test/debug_menu_ui.c`; the input handling in `src/debug.c` isn't.
    - Trainers, partners and decorations have it too (#123; `.names` is now 4 bits for the 9 kinds; `Debug_GetTrainerStepName`, `Debug_GetPartnerStepName`, `Debug_GetDecorationStepName`). The trainer and partner steps order by the trainer's own name, so Roxanne is under R, not LEADER, and May, Brendan and Steven can be jumped to: Set Flag's "CLASS NAME" order can't reach a "{PKMN} TRAINER" with Start, because it doesn't start with a letter. A name shared across rematches or by other trainers sits side by side by ID. The two steps moved to Warp's 28-tile window to show "ROXANNE  LEADER" with the party size on the ID line. Rematches can have the same party size too (Roxanne's third and fourth), and then only the ID differs. `TRAINER_NONE`, `PARTNER_NONE` and any other ID without a party are left out (they dial, as "None" or a red "Not enabled", and A takes them as before), and so is an unnamed decoration.
    - The first Start on the trainer step takes about 5.2 KB of heap at its peak (values 1,726, names 3,436, with headers), far below Set Flag's 28,648, and an estimated 4 frames, like the items or moves (it isn't measured: the test ROM has only 17 trainers). It keeps 1,726 bytes for the session, decorations 256 and partners 20, which takes about 2 KB off the headroom below. The weather, nature, Tera type and static outbreak lists and the map's trainer step stay on the digits: they are short.
    - Warp's map step has it too (#326, `DEBUG_STEP_NAMES_MAPS` on `sWarpMapNumSelectionStep`; `.names` now uses 10 of its 16 values, NONE included), across every map rather than the dialed group's: its name order goes by map index, which counts this game's 518 maps group by group (`Debug_GetMapIndex`, `Debug_GetMapGroupFromIndex`, `Debug_GetMapIndexName` in `src/debug_menu_ui.c`), and `DebugSelection_SetNameOrderValue` (`src/debug.c`) turns a pick back into a group, which it writes into the map group step (found through `DebugSelection_StepDataIndex`), and a map number. A pick in another group also keeps the map number in the map step's slot, so B then A comes back to it, and makes it Select's start, since the new group may not have the old number; the digit highlight moves down if the new group's last map number has fewer digits. The group and map steps still dial by number as before, and B from the map step shows the group the pick moved to. The hint takes the third line, where the region map section was. The outbreak location pickers keep the plain map step (`sMapNumSelectionStep`, no names). The names are unique, but many share a prefix, so a letter jump lands far from a map deep in P or R: the name search below gets there. The first Start sorts them in about 5.3 frames (1,452 ticks of the 1,024-cycle timer, measured in the test ROM with a throwaway test), taking about 3.1 KB of heap at its peak (values 1,036, names 2,072) and keeping 1,036 bytes for the session. Covered by "Map names:" and "Name order for maps" in `test/debug_menu_ui.c`; the step's input handling isn't.
    - Name search (#122): on any step with names, holding Select and pressing Start opens the naming screen's keyboard ("Name starts with:", up to 12 characters, `NAMING_SCREEN_DEBUG_SEARCH`, a small fork addition to `src/naming_screen.c`), and OK jumps to the first name in name order that starts with what was typed, with name order on, so Up/Down go on A-Z from there. Case and `é` fold as in name order, and the `_` in flag and map names is the charmap's hyphen, so type `-` for it. With no name that starts with it the value stays and the failure sound plays; an empty entry changes nothing. So that holding Select for it doesn't first send the value back to the step's start, Select pressed alone on a named step does that when it's let go (`selectPending`), not when it's pressed; another key while it's held takes the hold over and nothing resets, and a Start on the very frame it's let go still searches. Numeric steps without names reset on the press as before. `Debug_FindNamePrefix` (`src/debug_menu_ui.c`) binary-searches the order, building the step's order first if Start hadn't. The naming screen leaves the field, so `DebugSelection_StartNameSearch` (`src/debug.c`) fades out, keeps the input task's data and the step window's template in `sDebugMenuListData` and takes the menu down without freeing it; on the way back the objects are unfrozen before the field returns (their `frozen` flags outlive the old sprites, and a frozen object isn't frozen again, so the new sprites would run), and a `gFieldCallback` locks the field and freezes them, `Debug_ShowMenu` rebuilds the list, and the step comes back in a new window with the old task data (new window, list and icon ids), taking input once the fade-in ends. Covered by "Name search:" in `test/debug_menu_ui.c`; the keyboard round trip isn't.
  - Warp shows map.json names from `src/data/debug_map_names.h`, which `mapjson groups` generates (`generate_debug_map_names_text` in `tools/mapjson/mapjson.cpp`, a fork change to an upstream tool), read through `Debug_CopyMapName`, `Debug_GetMapCount` and `Debug_GetMapGroupName` in `src/debug_menu_ui.c` since #326. It is indexed like `gMapGroups`, with NULL for the other game's groups, which the group step refuses. "Recent warps…" (first in Utilities) lists this session's last 8 destinations from EWRAM, and Warp starts from the newest (#13). Above them, "Back to <map>" lands on the exact tile the last debug warp left (`sDebugWarpBack`, `WARP_ID_NONE` plus `gSaveBlock1Ptr->pos`), and records the tile it leaves in its place, so pressing it again goes back and forth; it isn't added to the destinations (#119; it warps through `SetWarpDestination`, whose coordinates reach Route 111's and 119's rows past 127 since #164). "Fly to map…" records the warp back too, but only once a destination is picked: `CB_ExitFlyMap`, `src/region_map.c`, calls `Debug_OnFlyMapExit`, which records it only if `sDebugFlyMapOpen` (set by the debug Fly) says the debug menu opened that fly map, so B on the map and the real Fly record nothing; the fly isn't a recent warp (#165). "Warp to x/y here…", after Warp, lands on a tile of the player's map (`sWarpToCoordsSelection`): X and Y steps from 0 to the layout's width and height less 1 (map coordinates, no `MAP_OFFSET`), starting on the player's tile, with the destination shown as it is dialed. It records the warp back, unless the tile is the player's own (A, A would lose it), and isn't a recent warp either, so "Back to <map>" now shows whenever the warp back is set, not only after a recent warp (#117). LTO drops all of it from the release ROM.
    - Favourites (#118): `DEBUG_WARP_FAVOURITES` in `include/config/debug.h` lists up to 11 `DEBUG_WARP_FAVOURITE(MAP_x, warp id)` entries, which "Recent warps…" shows after "Back to <map>" and before this session's warps, so they show before the first debug warp too ("No warps yet" now means no warp back and no favourites). It ships with six (Littleroot Town, Rustboro, Slateport, Lilycove and Ever Grande City, and the Battle Frontier's west side); empty it for none. Each entry expands to a `sDebugMenu_Actions_RecentWarps` row whose params is a compound-literal `struct DebugWarp`, and `Debug_GenerateListRecentWarpsMenu` labels every row from its option's params, with the option index as the row's id (the rows move up a place when the warp back isn't set). A favourite warps as a recent warp does and records the warp back (`DebugAction_Util_FavouriteWarp`), but isn't added to the recent warps, so it isn't listed twice and doesn't push out a dialed warp; Warp still starts from the newest recent warp. A favourite that isn't a map and warp of this game (`Debug_IsMapWarpInGame`, `src/debug_menu_ui.c`: a map past `Debug_GetMapCount`, such as an FRLG map, or a warp id past the map's last, other than warp 0 of a map without warps) shows its warp id, as "? (0)" for an FRLG map, and plays the failure sound. A `STATIC_ASSERT` keeps the list within `DEBUG_MAX_MENU_ITEMS`. Covered by "Map names: a warp favourite" in `test/debug_menu_ui.c`; the list isn't.
  - Set Flag and Set Var show the flag's or var's constant name (without `FLAG_`/`VAR_`, "-" for one without a name) on the second line of Warp's 28-tile window, and Start gives name order on the flag and var ID steps (`DEBUG_STEP_NAMES_FLAGS`/`VARS`). The first Start on Set Flag sorts its 2,381 names (the 1,527 constant names and 854 trainers) in about 22 frames, Set Var's 256 in about 1.3 (#137; #14's merge sort took 42 frames for the constant names alone, and 3 for the vars).
    - Heap headroom (#226, no code change): Set Flag's sort takes 28,648 bytes of the 115,968-byte `gHeap` at its peak, in three blocks with their 16-byte headers (values 4,800, names 9,596, the built trainer names 14,204). Measured on the debug-menu ROM with the owner's debug save, run headless in `tools/mgba/mgba-rom-test-mac` with a throwaway probe (not committed) that fed the keys and logged the heap blocks:
      - The field holds 11,728 bytes (the three overworld BG tilemaps and the message window), and Set Flag's step 19,860 (with `sDebugMenuListData` and its 28-tile window). With the species, item, move and Var orders already built in that session, in the Lilycove Contest Hall or Lilycove City, it holds 27,028 before the sort and 55,676 at its peak, which leaves a 59,864-byte free block.
      - A Gen 5 map popup still up when the menu opens takes 5,792 more (two windows), so the worst case seen is about 54,000 bytes spare. Nothing checks it: rerun such a probe if an upstream sync adds many flags or trainers (6 bytes of heap each, and a trainer's built name about 17 more).
    - A trainer flag shows its trainer's class and name from `gTrainers` instead, such as "LEADER ROXANNE" (`Debug_CopyTrainerFlagName`, `src/debug_menu_ui.c`), and "-" for a trainer without a party (`TRAINER_NONE`) and the unused IDs from `TRAINERS_COUNT` on (#136). Name order sorts them by that name too (#137): the flag step's `DebugNameFunc` is `Debug_GetFlagDisplayName`, which builds a trainer's name in the caller's buffer (`DEBUG_NAME_BUFFER_SIZE`), and `Debug_BuildNameOrder` copies the built names into one heap block (about 14 KB for the 854 trainers) while it sorts. The letter jump binary-searches the order (`Debug_FindNameInitial`), so it builds about 12 names a press, not one per name.
    - `tools/misc/make_debug_flag_var_names.py` generates the gitignored `src/data/debug_flag_var_names.h` from `flags.h`, `flags_frlg.h`, `vars.h`, `vars_frlg.h` (under `#if IS_FRLG`: `vars.h` includes it in every game) and the configs, whose flag aliases such as `I_EXP_SHARE_FLAG` (the fork's `FLAG_UNUSED_0x264`) are shown whole. Read the names through `Debug_GetFlagName`/`Debug_GetVarName` in `src/debug_menu_ui.c`.
    - The compiler computes the values (many need enums), so every entry is `#if defined(...)`-guarded and indexed through a macro that sends values outside the table to an unread last slot. Where names share a value, the last initializer wins (`-Woverride-init` is off in that header), and the generator orders the entries so that the first defined real name beats a config alias, which beats `UNUSED` placeholders and `_START`/`_END`/`_COUNT` markers.
    - Behind `DEBUG_FLAG_VAR_NAMES` (`include/config/debug.h`, TRUE): about 50 KB of the debug-menu ROM, none of the release ROM. Covered by `test/debug_menu_ui.c` and `python3 -m unittest discover -s tools/misc` (in CI); the picker display isn't.
